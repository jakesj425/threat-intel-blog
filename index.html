Opinion of a DFIR Guy

🔥 DFIR Flavor of the Day: JSONPing Callbacks, Fake Webex Lures, and npm Gone Rogue 🔍

🔗 Thing #1: Kimsuky invented "JSONPing" — payload pages that phone home via JSONP to verify you actually ran the malware. The distribution site pings localhost servers in real time to confirm execution before dropping the next stage. Clever? Painful. For DFIR: your web logs now show callback requests to localhost domains. That's a smoking gun most people miss. And they spoofed real Webex meeting pages using actual meeting schedules. The social engineering tailoring is next-level. Source

🔗 Thing #2: Three-stage HttpSpy replaced the old single-binary loader with RC4 encryption at every hop. The new variant uses `memloader` → `spyloader.dll` → `spyinster.dll`, each layer encrypted. For DFIR: you can't grep for strings anymore. Memory forensics is the only way to see what stage two and three are doing. And those C2 domains? `chickenkiller.com` and `crabdance.com` — free dynamic DNS they keep rotating through. Source

🔗 Thing #3: SideCopy hit Afghanistan's Ministry of Finance with Pashto-language LNK files disguised as staff directories. They listed real provincial finance officials with working contact info as decoys. The chain goes LNK → mshta.exe → remote HTA → obfuscated JS → XenoRAT 1.8.7 beaching to bulletproof Bulgarian hosting. For DFIR: the registry persistence key mimicked Microsoft Edge. If you only check Run keys, you'll miss it. Always check `URL` handler hijacks too. Source

🔗 Thing #4: JINX-0164 trojanized `@velora-dex/sdk` on npm, but the rad part is the INITIAL ACCESS. LinkedIn recruiter persona → fake Zoom audio driver download → AUDIOFIX Python infostealer → MINIRAT Go backdoor → then CI/CD pivoting. For DFIR: the npm supply chain hook isn't the story, it's the final move. Most responders will look at the trojanized package and stop there. Hunt the LinkedIn DM trail. Source

🔗 Thing #5: Sapphire Sleet's macOS campaign uses Apple Script Editor and Finder to execute code OUTSIDE security enforcement boundaries. They suppress system alerts during fake Zoom SDK updates. For DFIR: EDRs that rely on macOS system extension monitoring will miss Finder-spawned processes entirely. TCC bypasses built in. This is why file access auditing (not just process monitoring) matters on Mac. Source

The big picture? Defense evasion is now about abusing trusted tools, not avoiding them. Finder, mshta, AppleScript, npm postinstall — attackers live inside the OS toolkit. Your detection has to start with "what abnormal thing is this trusted binary doing?" not "is this binary bad?"
